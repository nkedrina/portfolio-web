# Реестр функций и механизмов portfolio-web

Основа реестра: реальный код из `render.js`, `data.js`, `utils.js`, `script.js` и HTML-оболочек. Этот документ не заменяет `PROJECT_MAP.md`: здесь фиксируются конкретные функции, вызовы, состояния и риски изменений.

## Критическая цепочка загрузки

На основных HTML-страницах скрипты загружаются в порядке:

1. `data.js` — нормализует и публикует `window.PORTFOLIO_DATA`.
2. `utils.js` — публикует `window.PORTFOLIO_UTILS`.
3. `render.js` — читает обе глобальные структуры, инициализирует интерфейс и hash-маршрутизацию.

В `exhibitions.html` и `contacts.html` дополнительно первым загружается `script.js`. Он устанавливает собственный `window.PORTFOLIO_DATA`, затем `data.js` устанавливает актуальный объект поверх него. Поэтому важные механизмы чтения данных зависят фактически от `data.js`, а не от `script.js`.

# Реестр функций

## 1. Нормализация данных и медиа

### `window.toAssetUrl(src)`

- Файл: `data.js:5-18`.
- Назначение: преобразовать строковый путь медиа или оставить внешние/специальные URL без изменений.
- Вход: `src` — произвольное значение или строка.
- Результат: исходное значение или локальный относительный путь.
- Логика:
  - возвращает `null`, пустое значение или нестроку без изменения;
  - приводит обратные слеши к `/`;
  - не меняет абсолютные HTTP(S), протокол-относительные URL и `data:` URL;
  - удаляет начальные слеши у локальных путей `images/` и `projects/`.
- Зависимости: нет внешнего хранилища.
- Где используется:
  - через `normalizeAssetUrls()` при загрузке `data.js`;
  - косвенно через `window.normalizeAssetUrls(A/CATS/PROJECTS/EXH)`;
  - нет прямых вызовов по функции из `render.js`.
- Изменяемые данные: не изменяет исходную строку непосредственно вне вызова; может записать новый URL в объект вызывающей функции.
- Риск изменений: нельзя начинать префиксом нормализовать уже внешние URL, иначе поломаются CDN-ссылки и ссылки Behance/Telegram. Изменение правила для `projects/` и `images/` затронет все проектные и общие медиа-ссылки.

### `window.normalizeAssetUrls(value)`

- Файл: `data.js:20-37`.
- Назначение: рекурсивно нормализовать все строковые поля массивов и объектов данных.
- Вход: массив, объект или примитив.
- Результат: тот же тип с заменёнными строковыми медиа-полями.
- Логика: рекурсивно обходит массивы и собственные поля объекта; строки передаёт в `toAssetUrl()`; вложенные объекты обрабатывает рекурсивно.
- Зависимости: `window.toAssetUrl()`.
- Использование: непосредственно для `A`, `CATS`, `PROJECTS`, `EXH` перед публикацией `window.PORTFOLIO_DATA` в `data.js:228-233`.
- Изменяемые данные: mutate-подход: исходные массивы и объектные поля изменяются на месте.
- Риск изменений: рекурсивное изменение строковых полей может затронуть не-медиа ссылки, если они совпадают с распознанным расширением или префиксом. После изменения нельзя повторно считать, что исходные локальные пути сохранены в глобальных данных.

## 2. Вспомогательные функции

### `$()`

- Файл: `utils.js:4`.
- Назначение: короткая обёртка над `querySelector` для работы с DOM.
- Вход: CSS-селектор `s`, необязательный корень `r`.
- Результат: первый найденный элемент или `null`.
- Логика: выполняет `(r || document).querySelector(s)`.
- Зависимости: только DOM API.
- Использование: экспортируется как `window.PORTFOLIO_UTILS.$` и активно используется в `render.js` для `main`, `header`, `modal`, `quick`, `footer`, `toast`, hero и т.д.
- Риск изменений: изменение области поиска по умолчанию или возврата может повлиять на подавляющее большинство функций рендера.

### `esc(s)`

- Файл: `utils.js:6`.
- Назначение: экранировать текст перед вставкой в HTML-строки.
- Вход: любое значение `s`.
- Результат: строка с заменой `&`, `<`, `>`, `"` и `'` на HTML-сущности.
- Зависимости: нет.
- Использование: практически во всех HTML-генераторах `render.js` для заголовков, описаний, ссылок и подписей.
- Изменяемые данные: не изменяет входное значение; только создаёт строку.
- Риск изменений: ослабление экранирования создаёт XSS-риск при любом пользовательском или редактируемом контенте; удаление экранирования для ссылок может сломать атрибуты.

### `sortedEx()`

- Файл: `utils.js:7`.
- Назначение: получить копию выставок, отсортированную по убывающей строковой дате `YYYY-MM`.
- Вход: нет явного входа; читает `window.PORTFOLIO_DATA.EXH`.
- Результат: новый отсортированный массив без изменения исходного `EXH`.
- Зависимости: глобальный объект `window.PORTFOLIO_DATA`.
- Использование: `home()` отбирает избранные выставки и `exhibitions()` формирует списки выставок/фестивалей.
- Риск изменений: формат даты должен оставаться сравнимым лексикографически (`YYYY-MM`). Сортировка уже использует копию, поэтому изменение исходного массива не происходит.

### `pad2(n)`

- Файл: `utils.js:8`.
- Назначение: форматировать число минимум до двух символов.
- Вход: число `n`.
- Результат: строка `n`, если она >=10, иначе `0n`.
- Использование: нумерация текстовых блоков и секций в `detailHTML()` через переменную `t`.
- Риск изменений: низкий; на нечисловом значении сохраняется текущее неявное преобразование JavaScript.

### `place(e)`

- Файл: `utils.js:9`.
- Назначение: собрать строку места из полей `city` и `country` события.
- Вход: объект выставки `e`.
- Результат: строка вида `city, country`, если одно поле отсутствует — только существующие поля.
- Использование: `exRow()`; косвенно через формирование подписи в списке выставок.
- Риск изменений: при изменении порядка или формата ожидается согласованная структура объекта `EXH`.

### `cityLine()`

- Файл: `utils.js:10`.
- Назначение: сформировать строку городов художницы.
- Вход: нет явного входа; читает `A.cities`.
- Результат: экранированный список городов через разделитель ` — `.
- Зависимости: `esc()` и `window.PORTFOLIO_DATA.A.cities`.
- Использование: hero главной и резервное значение поля `aboutMeta` в `about()`.
- Риск изменений: изменение типа `cities` с массива на другое значение сломает `.map()`.

### `TAG(t)`

- Файл: `utils.js:11`.
- Назначение: создать подпись раздела с разделителем и handle проекта.
- Вход: строка тега `t`.
- Результат: экранированный тег + `<i class="dot">` + `@nkedrina`.
- Использование: заголовки портфолио и секций в `home()`, `about()` и детальной странице проекта.
- Риск изменений: изменение разметки точки влияет на стили `.dot`, а изменение обработанного текста требует сохранения экранирования.

## 3. Маршрутизация и жизненный цикл страницы

### `normalizeInitialPath()`

- Файл: `render.js:630`.
- Назначение: при отсутствии hash преобразовать загрузку отдельного HTML-файла в hash-маршрут SPA.
- Вход: нет параметров; читает `location.hash` и `location.pathname`.
- Результат: устанавливает `location.hash` или ничего не делает.
- Логика: сопоставление выполняется по имени последнего сегмента пути: `index.html`, `about.html`, `portfolio.html`, `exhibitions.html`, `contacts.html`.
- Зависимости: объект `location`, браузерный history/hash API.
- Вызывается: один раз при инициализации в конце `render.js:689` перед `route()`.
- Изменяемое состояние: `location.hash`.
- Риск изменений: при деплоe в каталогах или с rewrite-маршрутами `split('/').pop()` может дать неверное имя; изменение HTML-оболочки потребует обновления карты.

### `route()`

- Файл: `render.js:631-640`.
- Назначение: главный hash-router приложения и реакция на смену адреса.
- Вход: нет параметров; читает `location.hash`, внутреннее состояние `current` и массив `PROJECTS`.
- Результат: вызывает рендер нужной страницы или редирект на портфолио при неизвестном проекте.
- Логика:
  1. закрывает quick-preview, если он открыт;
  2. распознаёт hash вида `#/portfolio/<id>`;
  3. проверяет существование ID в `PROJECTS`;
  4. неизвестный проект перенаправляет на `#/portfolio`;
  5. для `/contacts` рендерит главную страницу и прокручивает к секции контактов;
  6. для обычных страниц выбирает рендер из `routes`;
  7. при смене ключа вызывает `render()`;
  8. обновляет active-состояние навигации;
  9. закрывает modal и управляет прокруткой контактов/главной.
- Зависимости: `PROJECTS`, `routes`, `closeQuick()`, `closeModal()`, `render()`, `setNav()`, `scrollToContacts()`, `location.hash`, `history`.
- Вызывается: при начальной загрузке в конце `render.js:689` и на каждое событие `window.hashchange` в `render.js:671`.
- Изменяемые состояния: `current`, `main.innerHTML`, hash, активная навигация, прокрутка, quick/modal, `document.title`.
- Риск изменений: основная точка регрессии SPA. Изменение формата slug/ID или маршрута требует согласования с `pcard()`, `projectHTML()`, валидацией проекта и обработчиками ссылок.

### `render(page, pid)`

- Файл: `render.js:619-627`.
- Назначение: заменить содержимое `#main`, подготовить новое DOM-состояние страницы и вызвать гидратацию.
- Вход: `page` — ключ рендера (`/`, `/about`, `/portfolio`, `/exhibitions`, `/contacts`, `/project`); `pid` — ID проекта для страницы проекта.
- Результат: заполненный `main`, обновлённое состояние body/header и инициализированные медиа/анимации.
- Логика:
  - сбрасывает фильтр портфолио в `all` при входе на `/portfolio`;
  - для `/project` получает индекс проекта через поиск ID и вызывает `projectHTML(index)`;
  - для остальных страниц вызывает функцию из `routes[page]`;
  - перезапускает анимацию `main.enter`;
  - выставляет `body.home` для главной;
  - обновляет навигацию;
  - вызывает `hydrate()`, `setHero()`, `applyRuntimeAssetOverrides()`;
  - прокручивает окно вверх и сбрасывает состояние скрытого header.
- Зависимости: `routes`, `PROJECTS`, `pfCat`, `hydrate()`, `setHero()`, `applyRuntimeAssetOverrides()`, DOM-элементы `main/hdr`.
- Вызывается: только из `route()` при смене `current`.
- Изменяемые элементы: `#main`, `document.body`, активные `.nav a`, `document.title`, `#hero`, `#hdr`, прокрутка окна.
- Риск изменений: повторный рендер без обновления listeners не требуется для global document listeners, но DOM-ссылки внутри `main` заменяются. Изменение порядка вызова `hydrate()` и медиа-функций может отразиться на загрузке галереи.

### `setNav(key)`

- Файл: `render.js:628`.
- Назначение: синхронизировать атрибут `aria-current` навигации.
- Вход: ключ страницы (`/`, `/about`, `/portfolio`, `/exhibitions`, `/contacts`).
- Результат: добавляет/удаляет `aria-current="page"` у `.nav a`.
- Где вызывается: из `route()` и `render()` косвенно через локальный цикл навигации в `render()`.
- Риск изменений: ключи должны совпадать с `data-p` в HTML; проектная страница передаётся как `/portfolio`.

### `onScroll()`

- Файл: `render.js:643-644`.
- Назначение: скрывать/показывать header при прокрутке и различать верх страницы.
- Вход: читает `window.pageYOffset`, внутренние `lastY`, состояние `body.lock`.
- Логика: в верхних 24 px header всегда открытый и получает класс `top`; при прокрутке вниз после 120 px скрывает header; при прокрутке вверх показывает; блокирует изменение при открытом `body.lock`.
- Вызывается: scroll-listener через `requestAnimationFrame`, а также `render()` и при фокусе header.
- Изменяемые элементы: классы `.hdr`: `top`, `hide`; `body.hh`; внутренний `lastY`.
- Риск изменений: несогласованный `lastY` при смене страницы сбрасывается в `render()`. При `body.lock` header не управляется прокруткой.

## 4. Рендер основных страниц

### `home()`

- Файл: `render.js:297-307`.
- Назначение: создать HTML главной страницы.
- Вход: глобальные `A`, `PROJECTS`, `EXH`, `CATS` не передаются явно.
- Результат: строка HTML с hero, блоком обо мне, избранными проектами, избранными выставками и контактами.
- Логика:
  - берёт до 6 проектов с `featured === true`;
  - сортирует выставки через `sortedEx()` и берёт до 5 с `featured === true`;
  - формирует карточки через `pcard()`;
  - формирует строки выставок через `exRow()`;
  - включает `contactsBlock(false)`.
- Зависимости: `A`, `PROJECTS`, `EXH`, `sortedEx()`, `cityLine()`, `pcard()`, `exRow()`, `photoFigTheme()`, `practiceText()`, `contactsBlock()`, `TAG()`.
- Вызывается: `routes['/']` из `render()`.
- Изменяемые состояния: без боковых эффектов, кроме генерации HTML; реальное изменение DOM происходит в `render()`.
- Риск изменений: жёсткие лимиты 6 проектов/5 выставок и точные поля `featured/category/image` являются бизнес-правилами главной страницы.

### `about()`

- Файл: `render.js:309-311`.
- Назначение: создать страницу «Обо мне».
- Вход: глобальный объект `A`.
- Результат: HTML страницы с фото, bio, образованием, воркшопами, artist statement и переходами.
- Логика: локальная вложенная функция `rows(arr)` переводит массив `{years,text}` в строки и разбивает `text` по разделителю ` — ` на основную и дополнительную подпись.
- Зависимости: `A`, `photoFig()`, `dlRow()`, `cityLine()`, `TAG()`, `esc()`.
- Вызывается: `routes['/about']` из `render()`.
- Риск изменений: формат строки `text` разделяется строго по ` — `; изменение структуры `education/workshops/experience` может потребовать отдельного рендерера.

### `portfolio()`

- Файл: `render.js:349-352`.
- Назначение: создать страницу каталога проектов и кнопки фильтра.
- Вход: глобальные `CATS`, `PROJECTS`, внутренний `pfCat`.
- Результат: HTML header, chip-навигации и контейнера `#pfList`.
- Логика: создаёт кнопку `all`, затем по каждой категории создаёт кнопку с `data-cat` и начальным `aria-pressed`.
- Зависимости: `CATS`, `pfCat`, `pfHTML()`, `esc()`.
- Вызывается: `routes['/portfolio']` из `render()`.
- Риск изменений: названия и ID категорий должны совпадать с `PROJECTS[].cat` и ключами `PROJECT_SECTION_ORDER`.

### `pfHTML()`

- Файл: `render.js:326-341`.
- Назначение: построить отфильтрованный и упорядоченный HTML портфолио.
- Вход: нет явного параметра; читает `pfCat`, `CATS`, `PROJECTS`, `PROJECT_SECTION_ORDER`.
- Результат: HTML строки mosaic-сетки.
- Логика:
  - при `pfCat === all` берёт все проекты;
  - иначе берёт проекты с `p.cat === pfCat`;
  - для известной категории сортирует по индексам `PROJECT_SECTION_ORDER[c.id]`;
  - неизвестные проекты добавляются в конец;
  - передает финальный список в `mosaic()`.
- Зависимости: `mosaic()`, `PROJECTS`, `CATS`, `PROJECT_SECTION_ORDER`, `pfCat`.
- Использование: `portfolio()` и `pfUpdate()`.
- Изменяемые данные: исходный `PROJECTS` не мутирует, сортирует копию в одной ветке.
- Риск изменений: порядок является двойным: массив `PROJECTS` содержит обратный хронологический порядок, а `PROJECT_SECTION_ORDER` задаёт канонический порядок внутри категории.

### `pfUpdate(scroll)`

- Файл: `render.js:343-347`.
- Назначение: обновить сетку портфолио после изменения фильтра.
- Вход: `scroll` — обновлять ли прокрутку к сетке.
- Результат: перерисованный `#pfList`, актуальные `aria-pressed` на chip-кнопках и необязательная прокрутка.
- Логика: заменяет `innerHTML`, вызывает `hydrate()`, перезапускает animation-класс `swap`, обновляет состояние chips и прокручивает сетку кверху при необходимости.
- Зависимости: `#pfList`, `pfHTML()`, `hydrate()`, `pfCat`, `RM`, `window.pageYOffset`.
- Вызывается: документным click-handler при элементе `[data-cat]` в `render.js:659`.
- Изменяемые элементы: `#pfList.innerHTML`, атрибуты `.chip`, прокрутка окна.
- Риск изменений: принудительная прокрутка может мешать доступности и навигации; повторная установка `innerHTML` создает заново все карточки и медиа-наблюдатели.

### `mosaic(list)`

- Файл: `render.js:314-324`.
- Назначение: собрать адаптивную чередующуюся сетку карточек портфолио.
- Вход: массив проектов `list`.
- Результат: строка HTML сетки `.mosaic`.
- Логика:
  - чередует строки по 3 или 2 карточки;
  - если осталось <=3 проектов, берет оставшиеся целиком;
  - строка из 1 проекта получает класс `one`;
  - ширины задаются массивами `W3`/`W2` через inline `grid-column:span`;
  - вызывает `pcard(p, 'arch', ...)`.
- Зависимости: `pcard()`.
- Риск изменений: часть визуальной композиции жёстко задается здесь и дополнительно CSS-классами. Изменение размеров сетки требует согласования с CSS-модулями mosaic.

### `exhibitions()`

- Файл: `render.js:354-356`.
- Назначение: создать страницу выставок и мероприятий.
- Вход: глобальный `EXH`, косвенно `sortedEx()`.
- Результат: HTML с заголовками «выставки» и «фестивали • мероприятия».
- Логика: разделяет отсортированный массив по `type === exh/fest` и мапит `exRow()`.
- Зависимости: `sortedEx()`, `exRow()`.
- Вызывается: `routes['/exhibitions']`.
- Риск изменений: изменение `type` или даты сломает фильтрацию/сортировку.

### `contactsPage()`

- Файл: `render.js:358-359`.
- Назначение: создать отдельную страницу контактов.
- Вход: нет явного параметра.
- Результат: заголовок, подзаголовок и `contactsBlock(true)`.
- Зависимости: `contactsBlock()` и `A` внутри него.

## 6. Проекты и галерея

### `projImg(p)`

- Файл: `render.js:163-168`.
- Назначение: выбрать способ отображения карточного медиа проекта.
- Вход: объект проекта `p`.
- Результат: `<img data-src>` или `<img data-art>` для lazy/Canvas-загрузки.
- Логика:
  - для `yandex-search-day` жёстко возвращает URL локальной cover с cache-buster;
  - если есть `p.image`, использует `urlImg(p.image)`;
  - иначе генерирует Canvas-заглушку через `artImg(p.art, ...)`.
- Зависимости: `nat()`, `urlImg()`, `artImg()`, поля проекта.
- Использование: `pcard()`, `quickHTML()`.
- Риск изменений: специальная ветка Yandex привязана к конкретному ID и актуальному версии запроса; изменение медиа-файла не требует изменения файла при наличии обычного `p.image`, но этот project всегда игнорирует `p.image` из-за ветки.

### `makeArt(art, w, h, v)`

- Файл: `render.js:152-156`.
- Назначение: сгенерировать и закэшировать data URL Canvas-графики проекта.
- Вход: объект `art`, ширина, высота, вариант `v`.
- Результат: JPEG data URL.
- Логика: формирует ключ из style/seed/variant/width/height; при cache hit возвращает готовый URL; иначе создает Canvas, вызывает `ART[art.style]`, применяет `grade()` и сохраняет JPEG в `artCache`.
- Зависимости: `ART`, `rng()`, `grade()`, DOM и Canvas API.
- Использование: `loadImg()` для элементов с `data-art`.
- Риск изменений: изменение размеров или seed меняет данные data URL и cache key. Отсутствующий `art.style` приведет к вызову `ART[undefined]` и runtime-ошибке.

### `rng(s)`, `hex(h,a)`, `bg(c,w,h,col)`, `grade(c,w,h)`

- Файлы: `render.js:51-53`, `render.js:136-150`.
- Назначение: низкоуровневые средства генерации Canvas-фона.
- Логика:
  - `rng()` — детерминированный PRNG на основе seed;
  - `hex()` — HEX в RGBA;
  - `bg()` — заливка фона;
  - `grade()` — читаемое пиксельное преобразование по blue/dark ramp и warm adjustment.
- Зависимости: DOM/Canvas и объект `ART`.
- Использование: только внутри механизма Canvas-артов через `makeArt()` и ART-функции.
- Риск изменений: visual/binary-нечеткие изменения; влияет на все проекты без реальных изображений и на seed-повторы.

### `artImg(art,w,h,v,alt)`

- Файл: `render.js:158-159`.
- Назначение: создать лениво загружаемую Canvas-placeholder.
- Вход: параметры арт-системы, размеры, вариант, alt-текст.
- Результат: `<img data-art="...">` с записью параметров в словарь `reg`.
- Зависимости: `reg/rid`, `esc()` и последующий `loadImg()`/`hydrate()`.
- Использование: когда проект не имеет `image`, а также в fallback галерей и портретных заглушках.
- Риск изменений: ID data-art зависит от счетчика процесса и регистрового словаря. Повторный рендер очищает DOM, но `reg` остается как кэш параметров.

### `urlImg(src, alt)`

- Файл: `render.js:161`.
- Назначение: создать лениво загружаемый обычный `<img>`.
- Вход: src и alt.
- Результат: `<img data-src>` с экранированным src/alt.
- Зависимости: `esc()`, `hydrate()`/`loadImg()`.
- Использование: подавляющее большинство проектных карточек, галерей и портретов.
- Риск изменений: src не преобразуется в Blob прямо здесь: это уже сделано в `data.js`, затем путь может участвовать в fallback `loadImg()`.

### `loadImg(im)`

- Файл: `render.js:170-185`.
- Назначение: загрузить ленивое медиа при попадании в viewport или вызове из галереи.
- Вход: DOM-элемент `<img>` с `data-art` или `data-src`.
- Результат: установленный `im.src` и класс `on`; при ошибке Blob-попытка возвращается к локальному пути.
- Логика:
  - для `data-art` регистрирует параметры и асинхронно делает `makeArt()`;
  - для `data-src` назначает `onload/onerror`, затем читает атрибут;
  - при первой ошибке если src начинается с Blob prefix, удаляет префикс и возвращается к локальному пути;
  - если src уже локальный, восстанавливает `dataset.src`.
- Зависимости: `makeArt()`, `reg`, `BLOB_BASE`, DOM, IntersectionObserver.
- Использование: вызвается через `IntersectionObserver`, `hydrate()` и `openModal()`.
- Риск изменений: повторная ошибка не должна повторять fallback; флаг `fallbackApplied` может мешать новым попыткам после смены источника. Удаление Blob-prefix должно сохранять точное соответствие локальным путям проекта.

### `hydrate(root)`

- Файл: `render.js:247-257`.
- Назначение: подключить lazy loading, reveal-анимации и расчет галерей к фрагменту DOM.
- Вход: корневой элемент (по умолчанию передается `document` или `main/modal/list/quick`).
- Результат: наблюдаемые изображения/анимации и рассчитанные галереи/hero media.
- Логика:
  - навешивает load-handler для перерасчета галерей;
  - наблюдает изображения через `imgIO` или сразу вызывает `loadImg()`;
  - для hero video навешивает `loadedmetadata`;
  - наблюдает `.rv` через `rvIO` либо сразу добавляет `.in`;
  - сразу вызывает обе layout-функции.
- Зависимости: `imgIO`, `rvIO`, `loadImg()`, `layoutProjectGalleries()`, `layoutProjectMedia()`.
- Использование: из `render()`, `pfUpdate()`, `openQuick()`, а также обработчиков загрузки в самом hydrate.
- Риск изменений: повторный вызов hydrate на уже имеющих обработчики картинки навешивает дополнительные listeners/load-observer подписки. Для статического DOM это может вызвать дублирование действий.

### `layoutProjectGalleries(root)`

- Файл: `render.js:190-240`.
- Назначение: адаптивно перерассчитать сетки проекта в строках из 1–3 медиа по реальным пропорциям.
- Вход: корневой DOM-элемент.
- Результат: CSS-переменные `--photo-ratio`, `--photo-width`, `--photo-height` и вставленные `.project-gallery-break` элементы.
- Логика:
  - получает `.project-media`-детей галереи;
  - вычисляет ratio у `<img>/<video>`;
  - удаляет старые break-элементы;
  - определяет rowSize по ширине gallery и window: 1 при <=700, 2 при <=900, иначе 3;
  - разбивает медиа на строки;
  - для 1 элемента делает ширину 80% gallery; для нескольких считает равномерную высоту по сумме ratio;
  - обновляет `gallery.dataset.count`.
- Зависимости: DOM, `getComputedStyle`, реальные `naturalWidth/naturalHeight` или `videoWidth/videoHeight`, CSS-переменные gallery.
- Использование: resize-handler, load-handler, `hydrate()`.
- Риск изменений: добавление обычного child элемента в `.project-gallery` исключается как не `.project-media`. Если медиа ещё не загружено, ratio fallback =1.5. Переключение темы или нового размера должно сохранять повторный вызов, иначе CSS-переменные останутся прежними.

### `layoutProjectMedia(root)`

- Файл: `render.js:691-700`.
- Назначение: установить реальное aspect-ratio hero-медиа проекта.
- Вход: корневой DOM-элемент.
- Результат: обновленный inline `aspectRatio` у `.ppage .slide .mhero` для изображений/видео.
- Логика: читает `naturalWidth/naturalHeight` или `videoWidth/videoHeight` и ставит точное соотношение до 4 знаков.
- Зависимости: DOM медиа, `hydrate()` loadedmetadata/load handlers, resize-handler.
- Использование: `hydrate()`, resize-handler, image/video load handlers.
- Риск изменений: вызывается в конце файла после `hydrate()` в runtime, но функция declaration-hoisted. Изменение структуры `.mhero` потребует обновления селектора.

### `projectBlocks(p)`

- Файл: `render.js:488-516`.
- Назначение: подготовить блоки галереи для рендера и удалить дублирующее первичное медиа.
- Вход: объект проекта `p`.
- Результат: копия/обработанный массив блоков галереи.
- Логика:

  - удаляет первый `full`, если он с cover/primary;
  - удаляет первый media из начального video/full, если primary;
  - в начальном grid удаляет primary-файлы из `first.images` (но присваивает измененный массив в первом объекте копии);

- Зависимости: `p.blocks`, `isPrimaryMediaRef()`.
- Использование: `detailHTML()`.
- Риск изменений: ключевой механизм дедупликации hero и gallery. Изменение порядка или названия файлов может скрыть единственное корректное медиа или оставить cover дважды.

### `projectDescription(p)`

- Файл: `render.js:456-463`.
- Назначение: получить расширенное описание проекта из отдельного объекта и вставить его в detail-содержание.
- Вход: объект проекта `p`.
- Результат: HTML `<div class="project-description-full">` или пустой div при отсутствии текста.
- Логика: получает массив строк `PROJECT_DESCRIPTIONS[p.id]`, trims whitespace и собирает `<p class="dbody">`.
- Зависимости: локальный словарь `PROJECT_DESCRIPTIONS:365-454`, `esc()`.
- Использование: единственный вызов внутри `projectHTML()`.
- Риск изменений: описания не берутся из `p.concept`/произвольных текстов `PROJECTS`; добавление описания требует изменить отдельный словарь. Формат p без записи остается без дополнительного описания.

### `detailHTML(p)`

- Файл: `render.js:518-558`.
- Назначение: создать HTML медиа-контента детальной страницы проекта.
- Вход: объект проекта `p`.
- Результат: строка HTML с резервными блоками или реальными block/full/grid/video.
- Логика:
  - берет `p.gallery` как очередь `pool`;
  - через локальный `ph()` возвращает gallery item или создаёт Canvas-placeholder;
  - получает очищенные блоки через `projectBlocks()`;
  - если блоков нет, создаёт набор fallback-блоков из full/grid;
  - для `text` создаёт секцию с lead/body;
  - для `full` и `video` создает `<figure>/<video>`;
  - для `grid` формирует `.project-gallery` с одним или несколькими `.project-media`.
- Зависимости: `projectBlocks()`, `urlImg()`, `artImg()`, `esc()`, `pad2()`, `p.gallery/p.art/blocks`.
- Использование: `projectHTML()` дважды: один раз для начального `detail`, а потом повторно для финального detail в теле projectHTML.
- Риск изменений: внутренний fallback может создать изображения даже для проектов, у которых нет реальной галереи. `p.gallery` и `blocks` имеют разную роль и не взаимозаменяемы.

### `projectHTML(i)`

- Файл: `render.js:561-599`.
- Назначение: построить полностью детальную страницу проекта.
- Вход: индекс проекта в массиве `PROJECTS`.
- Результат: HTML `.ppage` с hero, описанием, медиа, description, внешними ссылками и prev/next навигацией.
- Логика:
  - берет prev/next циклически через модульный переход;
  - maps `p.exhibitions` в записи `EXH`, хотя локальная переменная `exs` не используется в фактическом return;
  - два раза вызывает `detailHTML(p)`, фактически финальная переменная detail переопределяет начальную;
  - определяет primary media через специальные `detailHeroMap` или `projectPrimaryMedia(p)`;
  - вставляет project description после первой gallery или перед detail, если gallery отсутствует;
  - добавляет только ссылки Behance из `p.links`;
  - формирует prev/next links по индексам массива.
- Зависимости: `PROJECTS`, `EXH`, `nat()`, `detailHTML()`, `projectDescription()`, `projectPrimaryMedia()`, `urlImg()`, `artImg()`, `esc()`, `TAG()`.
- Использование: `route` через `render('/project', pid)` и legacy `openModal(id)`.
- Изменяемые данные: не изменяет массивы; создает HTML и local variables.
- Риск изменений: циклическая prev/next навигация зависит от порядка массива `PROJECTS`, а не от категории. Переменные `exs` и `ar` вычисляются, но не используются в return. Специальные mapping для нескольких проектов привязаны к конкретным ID.

## 8. Быстрый просмотр и modal-механизм

### `openQuick(id, from)`

- Файл: `render.js:614`.
- Назначение: открыть быстрый preview проекта поверх главной страницы.
- Вход: ID проекта и исходный DOM-элемент `from` для восстановления фокуса.
- Результат: заполненный `#quick`, открытый `body.lock`, фокус на кнопке закрытия.
- Логика: ищет проект в `PROJECTS`, сохраняет `quickFocus`, задает innerHTML через `quickHTML()`, снимает hidden, блокирует body и вызывает hydrate.
- Зависимости: `PROJECTS`, `quickHTML()`, `hydrate()`, `#quick`, `quickFocus`, `document.activeElement`.
- Вызывается: document click-handler при `[data-quick]` только если `body.home`.
- Риск изменений: переключение проекта или несоответствие ID не обновляет hash; фокус восстанавливается только при закрытии через сохраненный элемент.

### `closeQuick()`

- Файл: `render.js:615`.
- Назначение: закрыть quick-preview и восстановить фокус.
- Вход: нет явного параметра.
- Результат: скрытый `#quick`, очищенный innerHTML, снятый `body.lock`, восстановленный фокус.
- Зависимости: `quickEl`, `quickFocus`, DOM `document.contains()`.
- Вызывается: route, click-handler, keyboard-handler и открытие full project через `data-quick-full`.
- Риск изменений: изменение порядка close/route может временно оставить `body.lock` снятым или оставлять старый `quickFocus`.

### `quickHTML(p)`

- Файл: `render.js:613`.
- Назначение: собрать HTML предпросмотра проекта.
- Вход: объект проекта `p`.
- Результат: HTML панели quick с cover, title, year, medium, description/concept и ссылками.
- Зависимости: `projImg()`, `quickLinks()`, `esc()`, поля проекта.
- Использование: только `openQuick()`.
- Риск изменений: экранирование влияет на ссылочный/текстовый контент. Изменение структуры проекта требует изменения всех полей в панели.

### `behanceUrl(p)`

- Файл: `render.js:611`.
- Назначение: найти первую Behance-ссылку проекта или общий fallback на A.socials.
- Вход: объект проекта `p`.
- Результат: URL или пустая строка.
- Логика: сначала ищет ссылку среди `p.links`, где URL или label содержит Behance; если нет, ищет общий Behance в `A.socials`.
- Использование: `quickLinks()`.
- Риск изменений: выбор первого совпадения регулярен по label/URL и может выбрать несоответствующий ресурс при нескольких ссылках.

### `quickLinks(p)`

- Файл: `render.js:612`.
- Назначение: собрать ссылки внутри quick-preview.
- Вход: объект проекта `p`.
- Результат: HTML-строка со ссылкой полного проекта и Behance.
- Логика: на главной всегда добавляет `#/portfolio/<id>` через `data-quick-full`; затем добавляет найденный Behance.
- Зависимости: `document.body.home`, `behanceUrl()`, `esc()`.
- Использование: `quickHTML()`.
- Риск изменений: логика intentionally проверяет `body.home`, поэтому вне главной не добавляет ссылку полного проекта; изменение body-классов затронет quick-links.

### `openModal(id)` / `closeModal()`

- Файл: `render.js:601-608`.
- Назначение: legacy-механизм открытия проектного modal вместо обычной route-страницы.
- Вход: `openModal(id)` — строковый ID проекта.
- Результат: `#modal` заполнен `projectHTML(index)`, unlocked state снимается через `body.lock`, фокус переносится на close-кнопку.
- Зависимости: `PROJECTS`, `projectHTML()`, `hydrate()`, `#modal`, `#mbody`, `imgIO`, `loadImg()`, `lastFocus`.
- Статус вызовов:
  - `openModal(id)` **не вызывается ни одним обработчиком или route** в реальном коде;
  - `closeModal()` вызывается из `route()` при смене hash и в `render()`-flow через route, а также из других веток route;
- Повторяющийся механизм: modal остается в DOM и стилизациях, но актуальный route проекта рендерит проект в `#main` через `projectHTML()`, а не через `openModal()`.
- Риск изменений: правка modal-механизма не затронет проектную route-страницу до явного подключения. Modal может быть задокументирован как legacy-код, а его DOM-кнопки `[data-close]` обрабатываются document handler.

## 9. Тема и медиа-настройки

### Inline theme-init в HTML

- Файлы: `index.html:13-23`, `about.html:10-20`, `portfolio.html:10-20`, `exhibitions.html:10-20`, `contacts.html:10-20`.
- Назначение: установить тему до загрузки основных скриптов и до основного рендера.
- Логика:
  - читает `localStorage.theme`;
  - сохраняет `light` только при точном значении, остальное переводит в `dark`;
  - при отсутствии значения сохраняет `dark`;
  - при ошибке storage устанавливает `dark`.
- Зависимые механизмы: `toggleTheme()` в `render.js` использует тот же ключ `theme`.
- Изменяемые данные: `localStorage.theme` и `document.documentElement.data-theme`.
- Риск изменений: повторение логики в пяти HTML-файлах означает необходимость согласованно менять fallback/ключ во всех точках входа.

### `toggleTheme()`

- Файл: `render.js:647`.
- Назначение: переключить theme и сохранить его в localStorage.
- Вход: нет параметров; читает текущий `data-theme`.
- Результат: атрибут `data-theme=light/dark`, обновленные фоновые assets и CSS-переменные.
- Логика:
  - определяет противоположную тему;
  - localStorage write обернут в try/catch;
  - если доступен `startViewTransition` и нет reduced-motion, переключение выполняется через View Transition;
  - иначе добавляет временный класс `tchg` и применяет через timeout 700ms;
  - внутри apply обновляет `data-theme`, для главной вызывает `setHero()`, всегда вызывает `applyRuntimeAssetOverrides()`.
- Зависимости: `RM`, `localStorage`, `document.startViewTransition`, `setHero()`, `applyRuntimeAssetOverrides()`, DOM/CSS.
- Вызывается: document click-handler при `[data-theme-toggle]`.
- Изменяемые состояния: `data-theme`, localStorage, `.tchg`, hero asset, runtime CSS overrides.
- Риск изменений: storage failure не блокирует изменение DOM. Несовпадение inline-init и toggleTheme приведет к inconsistent first paint.

### `setHero()`

- Файл: `render.js:611`.
- Назначение: установить локальный hero-фон в зависимости от темы.
- Логика: для light выбирает `A.heroImageLight || A.heroImage || images/back-video-light.gif`; для dark — `A.heroImageDark || A.heroImage || images/back-video-dark.gif`; затем нормализует путь через `toLocalAssetUrl()`.
- Зависимости: `A`, `#hero`, `toLocalAssetUrl()`, таймер `setTimeout`.

### `toLocalAssetUrl(src)`

- Файл: `render.js:18-21`.
- Назначение: нормализовать локальный медиа-путь для runtime override hero/portrait.
- Вход: строковый src.
- Результат: локальный относительный путь или внешний URL без изменений.
- Логика: заменяет обратные слеши и удаляет начальные слеши.
- Использование: `applyRuntimeAssetOverrides()`, `setHero()`.

### `applyRuntimeAssetOverrides()```

- Файл: `render.js:28-49`.
- Назначение: принудительно обновить локальные CSS-фоны после theme switch/рендера.
- Результат: создает или обновляет `<style id="local-runtime-asset-fix">`, переопределяет портреты и hero для светлой и тёмной темы.
- Логика: выбирает локальные portrait/hero-пути под theme и пропускает через `toLocalAssetUrl()`.

## 10. События и обработчики

### Document click-handler

- Файл: `render.js:650-663`.
- Назначение: единая точка обработки пользовательских кликов через делегирование.
- Вход: объект `MouseEvent` `e`.
- Обрабатывает в порядке приоритетов:
  1. `[data-theme-toggle]` → `toggleTheme()`;
  2. `[data-quick]` только на главной → `openQuick()`;
  3. `[data-quick-full]` → закрывает quick и меняет hash;
  4. close quick/backdrop → `closeQuick()`;
  5. `[data-top]` → `window.scrollTo({top:0})`;
  6. `[data-file]` → если путь отсутствует в `A`, отменяет переход и вызывает `toast()`;
  7. `[data-cat]` → меняет `pfCat` и вызывает `pfUpdate(true)`;
  8. `[data-scroll]` → плавно прокручивает до селектора;
  9. `[data-close]` → hash `#/portfolio`;
  10. hash-ссылки, если уже ведут на тот же hash → предотвращают повторный route и прокручивают страницу или contacts.
- Зависимости: большинство функций рендера, `A`, `pfCat`, `quickEl`, `modal`, `RM`.
- Изменяемые состояния: theme, quick/modal, hash, filter, прокрутка, toast.
- Риск изменений: один глобальный handler с hard-coded priority. Новые элементы с несколькими `data-*` атрибутами попадут на первый подходящий маршрут и могут не дойти до последующих веток.

### Document keydown-handler

- Файл: `render.js:664-669`.
- Назначение: keyboard-accessibility для quick-preview и modal.
- Логика:
  - если quick открыт: Escape закрывает; Tab ограничивает фокус первым/последним control;
  - если modal hidden: дальше выход;
  - Escape modal: hash `#/portfolio`;
  - стрелки вправо/влево выбирают prev/next `.mnav a` в modal;
  - Tab ограничивает фокус control elements.
- Зависимости: `closeQuick()`, `quickEl`, `modal`, DOM-события и hash-router.
- Риск изменений: modal фактически legacy и почти не открывается. Основная route-страница проекта не имеет собственного кода для keyboard prev/next в этом handler, кроме обычных hash-ссылок.

### Global scroll, resize и hashchange handlers

- Файл: `render.js:242-244`, `render.js:646`, `render.js:671`.
- Назначение:
  - resize пересчитывает gallery и project media через 120ms debounce;
  - scroll вызывает `onScroll()` через `requestAnimationFrame` и throttling;
  - hashchange вызывает `route()`.
- Зависимости: `galleryResizeTimer`, `ticking`, `onScroll()`, `layoutProjectGalleries()`, `layoutProjectMedia()`, `route()`.
- Риск изменений: resize observer и raf используются напрямую; при SPA-переходах debounce может примениться к DOM старой страницы до следующего рендера. Изменение selector gallery может оставить старые inline-variables.

### MutationObserver title

- Файл: `render.js:682-687`.
- Назначение: принудительно приводить регистр текста `document.title` к lower-case.
- Логика: наблюдает `<title>`, при изменении childList читает `.toLower()` и если отличается — устанавливает `.title` в нижнем регистре.
- Использование: один раз при инициализации приложения.
- Риск изменений: наблюдение может порождать цикл изменений в редких случаях; также принудительно используется нижний регистр названия, несмотря на route-названия из объекта `titles`.
- `titles` в `render.js:363` задаётся, но фактически **не используется** рендером: `document.title` всегда устанавливается в `@nkedrina` либо при существующем title нижний регистр нормализуется Observer.

## 11. Дубликаты, неиспользуемые и вероятно legacy-функции

Проверено статическим поиском имен и вызовов в `render.js`.

### Не вызываются из runtime-кода

- `openModal(id)` — определена, но не вызывается ни route, ни DOM-handler. Актуальная route-проектная логика не использует modal.
- `socialLink(s)` — определена, но не вызывается ни внутри `contactsBlock`, ни в footer.
- Объект `titles` — определяется в `render.js:363`, но не используется при рендере.
- Переменные `exs` и `ar` в `projectHTML()` — вычисляются, но не читаются в возвращаемом HTML.
- `#mbody` в `openModal()` — код проверяет и прокручивает элемент, но в актуальной разметке modal/projectHTML класс/ID этого элемента не найден в проверенном коде.

### Повторяющиеся реализации

- Asset resolution: `window.toAssetUrl()/normalizeAssetUrls()` в `data.js` и `toBlobAssetUrl()` в `render.js` решают схожие задачи для одних и тех же локальных Blob/HTTP-путей.
- Theme initialization: inline-код повторен во всех пяти HTML-файлах с одинаковой логикой.
- Project data: `script.js` содержит автономную копию `A/CATS/PROJECTS/EXH`, но в актуальном load-порядке в `exhibitions.html`/`contacts.html` затем загружается `data.js`, который переопределяет `window.PORTFOLIO_DATA` актуальным набором.
- Project photo logic: `photoFig()` и `photoFigTheme()` дважды реализуют портрет; одна theme-independent, одна theme-aware.
- Social links: `socialLink()`, ручная логика внутри `contactsBlock()`, а также ручная логика footer повторяют рендер соцсети и Instagram-маркера.
- Modal и route project: `openModal()`/`closeModal()` и актуальная route логика в `route()+render()+projectHTML()` пересекаются по проектному HTML, но только route-путь вызывается.
- Конфигурация project description: фактические описания дублируют часть полей `PROJECTS` (`desc/concept`) и вынесены в отдельный словарь `PROJECT_DESCRIPTIONS` внутри `render.js`.

## 12. Не проверенные элементы runtime

- Реальный рантайм без запуска браузера не проверялся, поэтому точное число вызовов IntersectionObserver и состояние View Transition не подтверждены тестами.
- Не проверялись специфичные CSS-эффекты для всех responsive-состояний.
- Не проверялась фактическая доступность всех Blob/CDN URL и PDF-файлов.
- Не проверялись повторные вызовы Observer при навигации внутри уже открытой страницы.
- Не проверялось наличие устаревших ссылок на `openModal()` за пределами статического поиска по одному `render.js`; в HTML и остальных JS-файлах прямых вызовов не найдено.

## 13. Тематическое отображение контента

### Theme init (inline-скрипты HTML)

- Файлы: `index.html`, `about.html`, `portfolio.html`, `exhibitions.html`, `contacts.html`.
- Назначение: применить сохранённую тему до загрузки основного рендера и предотвратить первый кадр с неправильной темой.
- Вход: `localStorage.theme`.
- Результат: `data-theme="light"` или `data-theme="dark"` на `<html>`; при отсутствии ключа сохраняется `dark`.
- Особенности: тот же ключ используется `toggleTheme()`; все HTML-файлы имеют повторяющуюся реализацию, поэтому изменение fallback или ключа нужно согласованно внести во все оболочки.

### `practiceText()`

- Файл: `render.js:274-276`.
- Назначение: выбрать краткое описание практики на главной по активной теме.
- Вход: `document.documentElement.data-theme`, поля `A.practiceLight` и `A.practice`.
- Результат: `<p class="soft about-copy">`.
- Текущая особенность: основной видимый текст задаётся псевдоэлементом `.about-copy::before` в `style.css`, а не реальным содержимым `A.practice`. В светлой теме используется отдельная строка `content`; в тёмной теме используется отдельная строка.
- Риск: изменение текста в `data.js` или старых TXT без изменения `style.css` может не изменить видимый текст главной.

### `photoFigTheme(cls)`

- Файл: `render.js:270-272`.
- Назначение: выбрать портрет главной страницы по активной теме.
- Вход: `data-theme`, `A.photoLight`, `A.photo`.
- Результат: `<img data-src>` для светлого или тёмного портрета.
- Светлая тема: `A.photoLight || A.photo`, в данных сейчас `images/me_2.jpg`.
- Тёмная тема: `A.photo || A.photoLight`, в данных сейчас `images/me_1.jpg`.
- Дополнительно: runtime override в `applyRuntimeAssetOverrides()` принудительно задаёт те же два портрета через `.about .fig::before`.

### Theme resources на странице «Обо мне»

- Файлы: `render.js:270-272`, `render.js:28-49`, `style.css:240-275`.
- Светлая тема: верхний портрет `images/me_4.jpg`, портрет блока bio `images/me_2.jpg`.
- Тёмная тема: верхний портрет `images/me_3.jpg`, портрет блока bio `images/me_1.jpg`.
- Общие текстовые поля bio, education, workshops и artist statement не имеют theme-specific вариантов в `data.js`.

### Общие и theme-dependent медиа проектных страниц

- Обложки и медиа проекта не меняются при переключении темы.
- Обложка общей карточки берётся из `projects/<имя-проекта>/cover.png` или Canvas `art`.
- Верхний блок страницы проекта берётся из `photos/1`, если этот файл указан в блоках проекта; это не `cover.png`.
- Остальные блоки берутся из пронумерованных файлов `photos/`.
- Переключение темы меняет фоновые CSS-переменные и hero-фон главной, но не сами project media.
